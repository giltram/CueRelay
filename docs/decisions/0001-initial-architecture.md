## 背景与约束

小型字幕组需要打轴、翻译、校对逐行并行；实时协作、本地视频不上传、过期编辑不能静默覆盖、审核绑定版本、ASS 不静默损失是已确定的要求。主要维护者熟悉 Django，且后续大量实现由 Coding Agent 完成；结构必须显式、依赖无环且便于小步验证。

仓库检查时为空，无根目录 AGENTS.md 或现有架构可继承；本次按会话提供的工程指令编写文档，M0 归档原文，不另写竞争规范。没有证据要求微服务、离线共同编辑、字符级协作或企业工作流。

## 选择、替代方案与代价

| --- | --- | --- | --- |

| 业务模块边界 | projects 拥有完整项目编辑业务，ass_format 独立纯格式模块，accounts 底层，HTTP/WS 是适配层 | 每个实体一个 app 容易形成 cue↔review↔lock 循环；把一切放进消费者/视图会重复规则 | 若出现独立职责再提取；保持公开命令/查询，不让边界成为 god file |
| 并发策略 | 整行 PostgreSQL 租约 + cue_version 乐观控制；每项目短事务串行分配序号并维护权限/样式一致性 | 字段锁允许同一行跨工种并行但组合条件复杂；仅乐观锁缺乏编辑提示；CRDT 解决当前未要求的字符协作；细粒度数据库锁更高吞吐但易遗漏跨对象竞态 | M1/M4 测项目锁热点；若 3–10 人预算达不到，先测量锁时间再细化，不移除版本校验 |
| HTTP/WS | HTTP 持久命令/快照/重放，WS 低延迟事件/租约/在线；共享 projects 入口 | WS 全命令可行，但需自建确认/重试/调试能力；HTTP 轮询全部数据会弱化低延迟体验 | 属实现建议；若改传输，保存/幂等/恢复语义仍保持 |
| 消息可靠性 | 同事务状态+ChangeEvent/成功回执，提交后尽力推送，数据库水位校验与重放兜底 | 只用 Channels 广播无法覆盖丢消息；事务 outbox/可靠队列可改善延迟保证但增加调度与运维 | 目前无需额外 worker；若未来要求更严实时 SLA/规模，再加持久分发，不把 on_commit 当可靠投递 |
| 审核 | 行显式提交；Review 追加不可变记录，绑定行版本/样式版本/媒体摘要；状态派生 | 只存 approved 布尔值会保留过期批准；对整个 project_seq 审核会因无关行修改全面失效；范围审核更符合部分上下文需求但模型更复杂 | 已确认简单逐行审核、成员兼任角色，沿用允许自审默认，不增加复杂工作流 |
| 样式 | 项目预定义样式；保守全局 style_revision；字体/位置/颜色不允许普通行标签任意覆盖 | 按样式局部失效可少重审但增加依赖跟踪；全禁格式标签太窄；开放任意标签损害统一风格 | M1 确认真正需要的标签；若频繁调样式导致重审过多，再设计局部失效 |
| 媒体 | 标准本地选片 + Object URL，Worker 增量完整 SHA-256；基准摘要固定 | 一次全读原生 digest 内存不可控；内容指纹/同画面跨编码映射复杂；服务器代理/解码违背不上传要求 | 已确认第一版固定项目视频，不支持中途更换片源 |
| 打轴能力 | 原生 video 先验证时间微调/试听与呈现精度，波形和本地解码按实验决定 | 直接承诺任意格式逐帧不可信；完整 WASM 解码/桌面本地辅助端更重但可能满足真实片源 | 已确认以字幕组真实片源的技术验证结果确定支持范围；优先播放与实际打轴，不先穷尽边界 |
| ASS | 明确可编辑子集 + 预检 + 原件保留；不支持文件整份保护性拒绝；P0 只向空项目导入 | 任意文件规范化风险是静默损失；全能力无损编辑成本过高；混合 opaque 行可编辑会引入样式/引用/重排依赖 | 已确认优先实际使用的基础功能，不支持内容保护性处理；具体基础覆盖按真实样本验证 |
| 历史 | 普通关系数据 + 追加前后值日志，P0 只读；P1 恢复是新命令 | Event Sourcing 要求迁移/重放语义；整项目快照覆盖恢复容易抹去别人新修改 | 无需额外确认；删除/恢复/拆并不得复用旧批准 |
| 前端与组件 | React/TS/Vite；媒体/副本/预览/UI 有明确边界；第三方库仅封装在责任模块 | Fork 整套编辑器可能继承不透明依赖；过早引入多层 store/通用插件架构增加理解成本 | 具体渲染/哈希/波形库须 S1–S3 与许可检查后选择 |

## 主要后果

此方案允许一个维护者用熟悉的栈，围绕少量可命名的业务命令建立测试和审计；新 Agent 可从文档和模块公开接口理解修改范围。代价是整行锁限制同一行并行编辑，项目级写锁限制热点吞吐，样式全局版本带来保守重审，受限 ASS 导入不能直接承接所有历史文件。

这些限制对初期小组可接受与否仍需真实用户和实验确认。视频字节留本地还意味着服务器无法独立证明客户端加载的媒体、浏览器刷新可能要重新选片、片源兼容与长片波形必须在客户端解决。

### D-R1

**已决：选择 A，显式恢复代号。** 用于识别数据库恢复后的不同历史，防止旧缓存、会话及未决命令直接沿用。实现及字段细节推迟到相关恢复机制开发阶段，不作为 M0 初始化与首个 M1 媒体/ASS 验证任务的前置工作。下表保留原有选项比较供追溯。

| 选项 | 主要收益 | 主要代价与必须证明的条件 |
| --- | --- | --- |
| A：显式恢复代号（已选择） | 恢复备份后、重新开放服务前发布新代号；握手、快照、水位、重放和写入可明确识别历史不匹配，不依赖序号大小或在线通知 | 增加协议身份与恢复操作步骤；所有服务进程须一致切换，并在回执查询/命令执行前拒绝旧历史请求；旧草稿/未决记录须保留来源，不能自动转投新历史 |
| B：全量撤销会话并强制重新登录、取完整快照（未选择） | 可以复用认证与会话失效边界，减少专用历史字段 | 恢复前认证及编辑凭证须在服务端永久失效，备份中的旧 session 不能复活；覆盖休眠页面和全部 HTTP/WS 入口，新登录也不能把旧未决命令自动当作新请求；运维耦合与全员中断更明显 |

选择 A 的理由是恢复分支与普通重连可明确区分。原有 M4.4 恢复验收保留，届时验证相同/更大游标的旧客户端失效；不承诺备份恢复零数据损失，RPO/RTO 仍须实测。本轮不继续细化机制。

## 技术事实的依据与待验证部分

Channels channel layer 的组消息可在容量限制下丢弃，因此持久变更不能靠它保证交付；Django on_commit 在事务提交后执行，回调失败也不能撤回提交。这支撑“持久日志 + 水位补齐”，不构成系统延迟已达标的证据。[Channels 规范](https://channels.readthedocs.io/en/stable/channel_layer_spec.html)、[Django 事务文档](https://docs.djangoproject.com/en/5.2/topics/db/transactions/#performing-actions-after-commit)。

SubtleCrypto.digest 不支持流式输入，所以大文件需要专门的增量实现；video 的时间输入与实际呈现帧应分开测量。这支撑 S1/S2，而不是预先认可某个库性能。[MDN digest](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/digest)、[MDN currentTime](https://developer.mozilla.org/en-US/docs/Web/API/HTMLMediaElement/currentTime)。

候选库的官方资料、许可证和媒体限制集中在 [架构组件表](../architecture.md)，不在此重复列表。Redis 具体版本的许可也需确认，不能用陈旧的“统一 BSD”假设锁定部署。

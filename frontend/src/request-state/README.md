# Resource read ordering

`ReadOrder` owns monotonic data and feedback versions for one resource/query. `start()` identifies a read; `acceptData()` orders successful payloads and authoritative permission/resource denials; `acceptFeedback()` orders error display and successful error clearing. A transient failure must only call `acceptFeedback()`, so it cannot hide an older valid revocation or initial payload. A pending newer request never invalidates completed data.

App owns account/membership epochs and ignores reads from older epochs. ProjectsPanel creates one order per organization/query/enabled lifetime and ignores callbacks from replaced orders. It separately counts outstanding requests and always settles them, even when their result is ignored. `isLatest()` permits immediate page correction from the newest issued read. Older totals wait until all outstanding reads settle; the caller retains the last accepted total independently from newer transient feedback. A superseded latest list read retries the current query without depending on organization refresh success. User filter/manual page changes clear old query feedback; automatic page correction and same-query retries preserve relevant failures until successful recovery.

app-workspace shares an order across route reads, explicit reload and background status observations for the same actor/project. Clear, replacement or disabled session invalidates that context. A stale successful status cannot clear a newer denial. Confirmed save/split archive errors establish a new status ordering barrier at response time. Route readiness has a separate threshold: each route attempt records its start version and retains the fact that an eligible success has already recovered it, independently of subsequent permission changes. A stale route error cannot hide that recovered read-only editor. Each retry starts a new threshold. Only a newer accepted success can supersede a route error; transient failures cannot grant readiness. Older hidden polls may supply valid status data but cannot recover a later route load/error. A stale reload can replace the editor only when a newer successful observation confirms its exact revision/status; newer denial/archive/different-revision observations retain the draft. The workspace owns its status-check feedback separately from App operation/context messages, so ordered recovery clears only that resource’s errors. These consumers do not use this class for session identity decisions, write transport or editor state.

Dependencies: none. Public API and invariants are covered in `read-order.test.ts`; browser integration is in `browser-tests/context-refresh.mjs` and `browser-tests/resource-response-races.mjs`.
